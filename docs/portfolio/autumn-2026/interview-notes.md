# 面试讲解与简历事实

## 30 秒介绍

这是一个基于 Obsidian Markdown 的只读知识检索服务。既有系统解析标签、双向链接和笔记分块，通过增量向量索引和 Agent 返回来源。本轮补充可解释的混合检索，以及“岗位要求关键词—笔记正文证据—实践建议”的业务流程，并提供不依赖模型、密钥或 Obsidian 客户端的离线网页演示。

## 两条可直接用于简历的描述

- 基于 Python、FastAPI 与 Pydantic，在既有只读 RAG 服务上实现词法候选与 RRF 混合排序，保留生产默认向量检索及原 API 合同，为来源补充标题与分块标识，并验证增量索引兼容。
- 实现覆盖 12 项技术关键词的岗位证据对照，支持正文来源定位、缺记录提示和 Markdown 导出；通过零模型离线工厂、真实接口验收脚本及网页交互验证，自动生成三个公开岗位场景报告。

这些描述体现工程和业务闭环，不能替换成“模型准确率提升”“求职匹配率”或真实标注量。

## 关键问题

**为什么先用有限词表？**
目的是在现有项目和时间预算内交付可解释的业务流程。关键词提取可以稳定复现、定位原文、核对规则；其边界是无法完整理解 JD，也不能可靠判断否定、熟练度和职位优先级。结果保留原句，让结论受证据约束。

**混合检索怎么融合？**
分别取得向量和词法前 20 个候选，按 chunk.id 去重；每个列表从排名 1 开始累加 1/(60+rank)。融合值只用于排序，来源仍保留余弦值。离线词法来源不输出假余弦分数。

**为什么不默认改为 hybrid？**
目前只用 12 个固定向量的排序合同案例验证实现，尚无真实 Embedding 的同集召回收益证据，因此保留默认 vector。

**怎样避免错把 NoSQL 当作 SQL？**
先做 NFKC 与大小写规范化，拉丁别名增加相邻字母数字边界；正文片段使用原字符位置映射，保留全角字符和标点，不拿规范化文本冒充原文。标题或标签单独命中不计作正文证据，一篇笔记只返回一个片段。

**有来源是否说明答案正确？**
不说明。来源标识支持定位；生成答案是否逐句符合证据仍需要评测。岗位报告中的资料命中更不代表个人熟练度。

**没有真实模型怎样证明工程完成？**
离线演示注入真实词法检索器和摘录式回答器，走同一批 FastAPI 路由。测试阻止模型客户端和外部 HTTP 路径，检查笔记哈希不变，并将模式标记为 synthetic_offline；浏览器验证完整业务交互。

**如何接回真实模型？**
使用原生产入口及既有配置；只在显式配置 RETRIEVAL_MODE=hybrid 时启用混合排序。模型客户端、Agent 生成逻辑和 LoRA 配置边界保持原有行为。

**下一步只做什么？**
用固定公开问题集和已存在的本地 Embedding 模型，比较 vector/hybrid 的来源命中与排序结果，记录运行条件；拿到证据后才决定是否切换默认策略。本轮没有自动开展这一实验。
